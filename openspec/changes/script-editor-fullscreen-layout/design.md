## Context

当前脚本编辑器使用 800px 宽的 el-dialog，Monaco Editor 高度固定 400px，试运行区域与代码编辑上下排列。用户反馈空间利用率低，编辑体验不佳，希望升级为全屏左右分栏布局。

现有实现：
- ScriptView.vue（296行）：列表页 + 编辑对话框 + 查看对话框，逻辑耦合
- 试运行为单次 API 调用，结果以 el-alert + JSON 折叠展示
- ConfigCard.vue 已有配置摘要展示能力（统计标签 + 节点/代理组预览 + YAML 展开）

## Goals / Non-Goals

**Goals:**
- 全屏编辑页面，左右分栏布局，最大化代码编辑空间
- 左侧面板集成试运行交互：订阅源选择、步骤可视化、输入/输出卡片
- 可拖动分隔条调整面板宽度
- 页面离开保护（未保存提醒）

**Non-Goals:**
- 不改变脚本列表页的功能和布局
- 不改变脚本的存储方式（仍为 `data/scripts/*.js`）
- 不引入新的前端框架或 UI 库
- 不实现多脚本同时编辑

## Decisions

### D1: 全屏实现方式

- **选择**：新路由页面 `/scripts/edit/:name`
- **理由**：独立页面更清晰，路由可直接访问（支持书签、分享链接），浏览器前进/后退可用，不依赖 el-dialog 的生命周期管理
- **已考虑 alternative**：
  - el-dialog fullscreen：对话框内嵌全屏，但路由不可直达，浏览器导航不可用
  - 全屏对话框覆盖：同 el-dialog fullscreen 问题

### D2: 组件拆分策略

- **选择**：容器 + 左面板 + 右面板（3 个组件）
- **理由**：左面板（试运行交互）和右面板（代码编辑）职责清晰，各自独立维护。不需要过度抽取 composable，当前规模下组件拆分已足够
- **已考虑 alternative**：
  - 单组件方案：400+ 行单文件，后续维护成本高
  - 组件 + Composable：文件最多，对于当前规模过度设计

### D3: 左侧面板宽度

- **选择**：可拖动调整，默认 260px，最小 200px，最大 500px
- **理由**：不同用户对试运行面板的空间需求不同，可拖动提供灵活性
- **已考虑 alternative**：固定宽度 260px — 简单但不够灵活

### D4: 试运行执行流程

- **选择**：严格顺序执行（1→2→3，失败停止）
- **理由**：步骤间有依赖关系（步骤 2 依赖步骤 1 的订阅配置），分步执行能真实反映进度，失败时快速定位问题
- **已考虑 alternative**：
  - 分步确认：增加交互复杂度，打断心流
  - 一键执行 + 实时进度：无法在步骤间展示中间结果

### D5: 步骤展示形式

- **选择**：Element Plus el-steps 组件，direction=vertical
- **理由**：与项目现有 UI 风格一致，减少自定义样式维护成本
- **已考虑 alternative**：自定义步骤条样式 — 更灵活但维护成本高

### D6: 输入/输出卡片

- **选择**：两张卡片并存，复用 ConfigCard 组件
- **理由**：输入和输出同时可见便于对比，ConfigCard 已有完整实现（统计 + 预览 + YAML）
- **已考虑 alternative**：输出替换输入 — 丢失输入上下文，无法对比

### D7: API 设计

- **选择**：拆分为两个 API（preview-subscription + try-run）
- **理由**：分步调用能真实反映执行进度，步骤 1 失败时不执行步骤 2，避免无效的脚本执行请求
- **已考虑 alternative**：单 API 返回两份数据 — 无法分步展示进度，步骤 1 失败时仍会执行脚本

## Risks / Trade-offs

- [Risk] 页面离开保护可能与浏览器刷新/关闭冲突 → Mitigation: 使用 `onBeforeRouteLeave` 保护路由跳转，浏览器关闭使用 `beforeunload` 事件（可选）
- [Risk] 拖动分隔条在快速移动时可能卡顿 → Mitigation: 使用 `mousemove` + `requestAnimationFrame` 节流，限制最小/最大宽度
- [Trade-off] 新增路由页面 vs 对话框 → 增加路由配置和页面跳转逻辑，但获得更好的编辑体验和可直达 URL

# Brainstorm：添加登录功能与首次管理员初始化

## 背景

项目是 Clash 订阅管理中心，后端为 Java 21 + Spring Boot 3.2.5 的多模块 Maven 项目，REST API 与静态前端位于 `module-web`；前端为 Vue 3 + Vue Router + Element Plus + Axios。现有数据持久化以 JSON 文件为主，例如订阅源、Mihomo 实例、构建流程和定时任务都写入 `data/` 目录下的子目录。

当前应用没有认证机制，打开管理后台即可访问所有管理 API。目标是在不改变项目整体部署方式的前提下增加登录功能：首次打开如果没有管理员信息，则引导用户自动初始化管理员账号；初始化后再登录进入管理后台。

## 决策链

### Q1：首次打开时的登录与管理员初始化流程怎么呈现？

候选方案：

A. 独立初始化页
- 打开应用后检查管理员是否存在。
- 没有管理员则进入 `/setup`，创建管理员后跳转登录页。
- 优点：初始化和登录边界清晰。
- 缺点：前端多一个独立路由和页面流程。

B. 登录页自动切换初始化模式
- 前端只有一个 `/auth` 页面。
- 页面根据后端状态显示“初始化管理员”或“登录”表单。
- 优点：入口统一，用户路径短，实现分叉少。
- 缺点：页面必须明确表达当前是首次初始化还是普通登录。

C. 后台内初始化弹窗
- 先显示后台框架，再弹窗要求创建管理员。
- 优点：能沿用后台布局。
- 缺点：未初始化时展示后台外壳会造成已经可用的错觉，不适合作为安全边界。

决定：选择 B，统一 `/auth` 页面，根据后端认证状态自动切换初始化和登录模式。

### Q2：登录状态如何维护？

候选方案：

A. 服务端 Session + Cookie
- 后端保存会话状态，浏览器自动携带 Cookie。
- 适合自托管管理后台，前端实现简单。

B. JWT / Bearer Token
- 后端签发 token，前端保存并放到 `Authorization`。
- 更像开放 API，但要处理 token 存储、过期和刷新。

C. 固定管理密码 + 每次请求密钥
- 实现简单，但体验和安全边界弱。

决定：选择 A，使用服务端 Session + 浏览器会话 Cookie。

### Q3：管理员账号范围怎么定？

候选方案：

A. 仅支持一个管理员账号
- 符合个人/自托管管理后台，模型和 UI 最简单。

B. 支持多个管理员账号
- 未来可多人使用，但需要账号列表、创建、禁用等管理能力。

C. 先单管理员，数据结构预留多用户扩展
- 当前只做一个账号，但存储结构不完全堵死未来扩展。

决定：选择 A，MVP 仅支持一个管理员账号。

### Q4：管理员信息存储在哪里？

候选方案：

A. 沿用现有 JSON 文件数据目录
- 例如 `data/admin/admin.json`。
- 和项目当前持久化方式一致，部署简单。

B. 引入嵌入式数据库
- 如 H2/SQLite，账号安全和扩展更规范。
- 会引入新的持久层复杂度。

C. 通过环境变量配置管理员
- 适合容器部署，但不符合首次打开引导初始化体验。

决定：选择 A，管理员信息保存到现有 `data` 目录下的 JSON 文件。

### Q5：密码策略如何定义？

候选方案：

A. 只要求最小长度
- 例如至少 8 位，简单直接，适合个人部署。

B. 要求复杂度
- 大小写、数字、符号组合，更安全但增加初始化阻力。

C. 不做前端复杂校验，仅后端限制非空和长度
- 减少规则争议，安全主要靠哈希存储和部署环境。

决定：选择 A，密码至少 8 位，前后端都做校验，后端作为最终约束。

### Q6：初始化成功后怎么处理？

候选方案：

A. 自动登录并进入后台
- 首次体验最顺畅。

B. 跳转到登录表单，要求重新输入密码
- 安全感更强，确保初始化和登录是两个明确动作。

C. 显示初始化成功页，再由用户点击进入
- 更明确，但流程更长。

决定：选择 B，初始化成功后不自动登录，切回登录表单并要求重新输入密码。

### Q7：会话有效期怎么定？

候选方案：

A. 浏览器会话级
- 关闭浏览器后失效，简单且偏安全。

B. 固定过期时间
- 例如 24 小时，体验更稳定。

C. 提供“记住我”
- 可长期保持登录，但需要额外 token 和退出管理，不适合 MVP 首版。

决定：选择 A，使用浏览器会话级 Session Cookie，不提供“记住我”。

### Q8：技术实现路线如何选择？

候选方案：

A. Spring MVC Interceptor + 自定义 Session 认证
- 后端增加 `AdminAuthService`、JSON 文件仓库、`AuthController` 和拦截器。
- 未登录访问受保护 API 返回 401。
- 放行 `/api/auth/status`、`/api/auth/login`、`/api/auth/setup`、静态前端资源。
- 优点：依赖少，符合现有项目风格，适合单管理员自托管后台。
- 缺点：不像 Spring Security 那样覆盖复杂安全场景。

B. Spring Security + Session
- 引入 `spring-boot-starter-security`，配置 SecurityFilterChain、PasswordEncoder、Session。
- 优点：标准安全框架，长期扩展能力好。
- 缺点：对当前项目偏重，会带来更多默认行为和配置复杂度。

C. 前端路由守卫 + 后端轻量 token
- 登录后后端签发短 token，前端保存后带请求。
- 优点：实现独立于 Session。
- 缺点：与已选择的 Session + Cookie 方向不一致，token 存储带来额外安全取舍。

决定：选择 A，使用 Spring MVC Interceptor + 自定义 Session 认证。

## 确认后的设计

### 总体架构

登录功能放在 `module-web`，不引入数据库和 Spring Security。后端新增轻量认证子模块：管理员信息通过 JSON 文件保存在 `data/admin/admin.json`，密码只保存哈希；`AuthController` 提供状态查询、初始化、登录、登出接口；`HandlerInterceptor` 保护 `/api/**` 中除认证接口外的管理 API。未初始化时，认证状态接口返回“未初始化”，其他受保护 API 返回 401 或 403，避免未初始化状态下直接操作后台数据。

前端新增统一 `/auth` 页面。应用启动或路由切换时先请求 `/api/auth/status`：没有管理员时显示初始化表单；已有管理员但未登录时显示登录表单；已登录则进入原后台布局。初始化成功后不自动登录，而是切回登录表单并提示用户重新登录。Session 使用浏览器会话级 Cookie，关闭浏览器后自然失效。

### 后端组件与接口

后端新增边界：

- `AdminAccount`：单管理员模型，包含 `username`、`passwordHash`、`createdAt`、`updatedAt`。
- `AdminAccountRepository`：读写 `data/admin/admin.json`，只允许存在一个管理员。
- `AdminAuthService`：负责判断是否初始化、初始化管理员、校验登录、写入/清除 Session 状态。
- `AuthController`：
  - `GET /api/auth/status`：返回 `{ initialized, authenticated, username? }`。
  - `POST /api/auth/setup`：仅未初始化时允许，校验用户名非空、密码至少 8 位，保存管理员；不自动登录。
  - `POST /api/auth/login`：校验用户名密码，成功后写入 Session。
  - `POST /api/auth/logout`：清除 Session。
- `AuthInterceptor`：拦截 `/api/**`，放行 `/api/auth/**`；其余 API 要求 Session 中存在认证标记。
- 密码哈希：使用 JDK 自带 PBKDF2，例如 `PBKDF2WithHmacSHA256`，避免额外依赖；每个密码使用随机 salt，并保存算法、salt、hash、迭代次数等必要参数。

错误语义：未登录返回 401，重复初始化返回 409，参数不合法返回 400，用户名或密码错误返回 401 且不区分具体原因。

### 前端流程与 UI

前端新增认证 API 封装和 `/auth` 路由。路由守卫或应用根组件在进入后台页面前请求认证状态：

- `initialized=false`：跳转 `/auth`，页面显示“首次使用，创建管理员”表单。
- `initialized=true && authenticated=false`：跳转 `/auth`，页面显示登录表单。
- `authenticated=true`：允许访问原有后台页面。

`/auth` 页面使用 Element Plus 表单，统一标题为“Clash 订阅管理中心”。初始化模式需要用户名、密码、确认密码；登录模式需要用户名、密码。初始化成功后显示成功提示并切换到登录模式，不自动写入登录态。登录成功后跳转到用户原本要访问的页面，默认 `/subscriptions`。后台 header 右侧增加当前管理员名和“退出登录”按钮，点击后调用 logout 并回到 `/auth`。

Axios 响应拦截器遇到 401 时统一跳转 `/auth`，但认证接口自身的 401 只显示表单错误，避免登录失败时重复跳转。

### 异常处理、边界与测试

边界规则：

- 已初始化后再次调用 setup 返回 409，不覆盖现有管理员。
- 未初始化时 login 返回 400 或 409 类错误，提示先完成初始化。
- 密码最小长度为 8，前后端都校验；后端是最终约束。
- Session 只保存认证标记和用户名，不保存密码或哈希。
- 登出使当前 Session 失效。
- JSON 文件损坏时后端返回明确错误，不自动重置管理员，避免误触发“重新初始化”绕过安全边界。
- 静态前端资源和 `/api/auth/**` 永远不被拦截，否则首次页面无法加载。

测试范围：

- 后端单元/集成测试覆盖：未初始化状态、初始化成功、重复初始化失败、短密码失败、登录成功/失败、未登录访问受保护 API 返回 401、登录后访问成功、登出后失效。
- 前端构建验证 `npm run build`。
- 手动验证：首次打开显示初始化表单；初始化后回到登录；登录后进入后台；刷新页面保持当前浏览器会话；关闭浏览器会话后需重新登录；登出后无法访问 API。

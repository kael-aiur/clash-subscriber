# Mihomo 实例详情页 — 技术设计

## Context

当前 Mihomo 实例管理只有一个列表页面（`/mihomo-instances`），支持基本的 CRUD、健康检查和手动推送配置。用户无法深入了解每个实例的转发规则配置。

核心需求是为 Mihomo 实例增加详情页面，包含三个标签页（实例信息、转发规则、推送历史），其中转发规则标签页允许用户输入域名，系统从 Mihomo API 获取当前运行配置，解析规则匹配后用 Vue Flow 流程图展示完整的转发路径。

### 现有约束

- 前端技术栈：Vue 3 + TypeScript + Element Plus，路由使用 hash history 模式
- 后端技术栈：Java 21 + Spring Boot 3.2.5，HTTP 客户端使用 OkHttp
- Mihomo 实例模型只存储连接信息（API URL、Secret），不存储推送的配置
- 配置格式为 Clash/Mihomo YAML，包含 `rules`、`proxy-groups`、`proxies` 三个核心部分
- 代理组可以嵌套（一个代理组的 proxies 列表可以包含其他代理组名称）

## Goals / Non-Goals

**Goals:**
- 为 Mihomo 实例提供详情页面，包含实例信息、转发规则、推送历史三个标签
- 实现域名转发路径查询：用户输入域名，展示从规则匹配到最终出口的完整流程图
- 流程图支持代理组嵌套展开/折叠，展示分支路径
- 使用 Vue Flow 作为流程图可视化库，dagre 自动布局

**Non-Goals:**
- 不实现实时流量监控（只展示配置层面的转发规则）
- 不实现配置编辑功能（只读展示）
- 不实现规则修改或代理组调整功能
- 不支持 IP 地址查询（仅支持域名查询，IP-CIDR 规则只做展示）

## Decisions

### D1: 转发规则数据来源
- **选择**：从 Mihomo API 实时获取当前运行配置
- **理由**：最准确，能反映实例实际运行状态。相比存储最后推送的配置（可能与实际有偏差）或从构建管线获取（反映的是构建结果而非运行状态），实时 API 获取是最可靠的方式
- **已考虑替代**：
  - 存储最后推送的配置到本地 → 拒绝：可能与实际运行配置不一致（手动修改、其他系统推送等）
  - 从构建管线获取 → 拒绝：反映的是构建结果，不是实例运行状态

### D2: 流程图展示层次
- **选择**：可展开/折叠的交互式流程图
- **理由**：默认展示规则 → 代理组 → 最终出口的简洁视图，用户可点击代理组节点展开查看内部子组和具体代理节点。兼顾简洁和信息完整性
- **已考虑替代**：
  - 只展示到代理组级别 → 拒绝：信息量不足，无法看到具体节点
  - 一次性展示全部层级 → 拒绝：节点过多时可读性差

### D3: 前端可视化库
- **选择**：Vue Flow
- **理由**：基于 Vue 3 的节点图库，TypeScript 支持良好，支持自定义节点和连线样式，社区活跃
- **已考虑替代**：
  - D3.js → 拒绝：学习曲线陡峭，与 Vue 集成需要大量手动工作
  - Mermaid.js → 拒绝：文本描述生成图表，自定义能力和交互能力有限

### D4: 规则过滤方式
- **选择**：用户输入域名查询
- **理由**：典型 Clash 配置可能包含上千条规则，全部展示不现实。用户输入域名后系统匹配规则并展示对应路径，精确且高效
- **已考虑替代**：
  - 搜索 + 分组过滤 → 拒绝：仍然是先展示大量规则再过滤，初次加载体验差
  - 按域名模式聚合 → 拒绝：聚合后丢失具体规则细节

### D5: 代理组分支展示
- **选择**：带分支的路径查询
- **理由**：Select 类型代理组包含多个可选节点，展示所有分支能帮助用户了解所有可能的转发路径。URLTest/Fallback 类型也展示所有节点并标注类型
- **已考虑替代**：
  - 只展示当前选中节点 → 拒绝：无法看到全部可选路径

### D6: 解析架构
- **选择**：后端主导（后端解析 + 构建图数据，前端只渲染）
- **理由**：后端负责从 Mihomo 获取配置、解析 YAML、匹配规则、构建流程图数据结构，返回 Vue Flow 格式的 JSON。前端只负责调用 API 和渲染。逻辑集中，前端简单
- **已考虑替代**：
  - 前端主导（后端只代理配置获取）→ 拒绝：前端需要引入 YAML 解析库，逻辑复杂
  - 混合方案（后端解析配置返回结构化数据，前端匹配规则构建图）→ 拒绝：增加了中间数据结构的维护成本

## Risks / Trade-offs

- **[Risk] Mihomo 实例离线时无法查询** → Mitigation：查询前检查实例健康状态，离线时展示明确的错误提示。可考虑缓存上次成功获取的配置作为降级方案（Future Work）
- **[Risk] 大量代理节点导致流程图过于复杂** → Mitigation：代理组节点默认折叠，用户按需展开。dagre 自动布局保证节点不重叠
- **[Risk] Mihomo API 响应慢影响查询体验** → Mitigation：前端展示加载状态，设置合理的 HTTP 超时时间（如 5 秒）
- **[Trade-off] 后端主导 vs 前端主导** → 每次查询都需请求后端，但换来的是前端逻辑简单和配置解析的可靠性

## Migration Plan

本变更为纯新增功能，不涉及现有功能的修改或数据库变更：

1. 后端新增 API 端点和配置解析服务
2. 前端新增详情页面和路由
3. 修改列表页添加跳转链接

部署顺序：
1. 后端部署（新增端点不影响现有功能）
2. 前端部署（新增页面和路由）

回滚策略：移除新增的路由和页面即可回滚前端，后端新增端点不影响现有功能无需回滚。

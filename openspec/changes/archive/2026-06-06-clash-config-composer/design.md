# Clash 配置生成器 - 设计文档

## Context

### 背景

当前项目（Clash Subscriber）已经具备订阅源管理、节点合并、代理组处理、规则组管理等功能。用户需要一个独立的 "配置生成器"，支持 Clash Verge 等客户端获取动态组合的配置文件。

### 当前状态

- **订阅源管理**：module-subscription 模块，支持 CRUD 和远程获取
- **节点合并**：NodeMergeProcessor，支持合并多个订阅源的节点
- **代理组处理**：ProxyGroupProcessor，支持代理组重组
- **规则组管理**：data/rule-groups/ 目录，支持规则组存储
- **前端界面**：Vue 3 + Element Plus，已有订阅管理、规则组管理等页面

### 约束

- 复用现有模块，不新建独立模块
- 输出标准 Clash YAML 配置
- 支持 Basic Auth 认证
- 基于名称的 URL 路径

### 利益相关者

- **主要用户**：需要分享 Clash 配置给朋友或团队成员的人
- **最终用户**：使用 Clash Verge 等客户端的用户

## Goals / Non-Goals

**Goals:**
- 创建一个独立的配置生成器，支持动态组合订阅源、代理组、规则组
- 生成标准 Clash YAML 配置，可直接被 Clash Verge 等客户端使用
- 支持 Basic Auth 认证，保护配置访问
- 提供友好的 Web 界面，方便配置管理
- 支持基于名称的 URL 路径，方便分享

**Non-Goals:**
- 不支持定时重新生成配置（后续迭代）
- 不支持推送到 Mihomo 实例（已有功能）
- 不支持配置版本管理
- 不支持多用户权限管理

## Decisions

### D1：基于现有模块扩展

- **选择**：在现有模块基础上扩展，复用已有的订阅管理、规则组管理等功能
- **理由**：项目规模不大，复用现有代码更高效，维护成本低
- **已考虑 alternative**：
  - 新建独立模块（module-config-generator）：开发量较大，需要处理跨模块调用，可能存在数据同步问题

### D2：代理组节点匹配方式

- **选择**：使用包含关键词的方式匹配节点
- **理由**：简单直观，用户容易理解，满足大部分使用场景
- **已考虑 alternative**：
  - 正则表达式：功能强大但复杂，用户学习成本高
  - 排除关键词：使用场景较少，可以作为后续扩展

### D3：规则组管理方式

- **选择**：复用现有的 rule-groups 目录数据
- **理由**：避免数据冗余，保持数据一致性
- **已考虑 alternative**：
  - 在配置生成器中独立管理规则组：会导致数据冗余，维护困难

### D4：认证方式

- **选择**：Basic Auth 认证
- **理由**：Clash 客户端原生支持，配置简单，用户友好
- **已考虑 alternative**：
  - Token 认证（URL 参数）：安全性较低，URL 可能被记录
  - 自定义 Header：客户端配置复杂

### D5：URL 路径格式

- **选择**：基于名称的 URL 路径，如 `/api/config/{name}`
- **理由**：直观易记，方便分享
- **已考虑 alternative**：
  - 基于 ID：不够友好
  - 组合格式（名称+ID）：URL 较长

### D6：存储方式

- **选择**：JSON 文件存储，每个配置一个文件
- **理由**：与现有系统保持一致（data/config-profiles/ 目录），简单可靠
- **已考虑 alternative**：
  - 数据库：增加依赖，复杂度高
  - 单一 JSON 文件：并发问题，不易管理

### D7：基础信息配置

- **选择**：每个配置独立存储基础信息
- **理由**：灵活性高，不同配置可以有不同的基础设置
- **已考虑 alternative**：
  - 全局默认配置：灵活性不足

## Risks / Trade-offs

### 风险

- **[风险] 名称冲突** → 缓解措施：创建配置时检查名称是否已存在，返回 409 Conflict 错误
- **[风险] 订阅源获取失败** → 缓解措施：记录错误日志，返回缓存的配置或空配置
- **[风险] 规则组数据格式错误** → 缓解措施：添加数据验证，记录错误日志

### 权衡

- **[权衡] 简单性 vs 灵活性** → 选择简单性：使用包含关键词匹配而非正则表达式，降低用户学习成本
- **[权衡] 独立性 vs 复用性** → 选择复用性：基于现有模块扩展，减少开发量但增加耦合

## Migration Plan

### 部署步骤

1. **后端开发**
   - 添加 ConfigProfile 模型
   - 添加 ConfigProfileRepository
   - 添加 ConfigGeneratorService
   - 添加 ConfigController

2. **前端开发**
   - 添加配置列表页
   - 添加配置编辑页

3. **测试**
   - 单元测试
   - 集成测试
   - 手动测试

4. **部署**
   - 编译打包
   - 部署到服务器

### 回滚策略

- 保留旧版本的 jar 包
- 如果出现问题，回滚到旧版本

### 验收条件

- 能够创建、编辑、删除配置
- 能够通过 Basic Auth 认证获取配置
- 生成的配置可被 Clash Verge 正常使用
- 代理组节点匹配正确
- 规则组排序正确

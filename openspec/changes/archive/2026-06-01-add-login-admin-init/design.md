## Context

Clash 订阅管理中心当前没有登录机制，浏览器打开前端后即可访问订阅源、Mihomo 实例、构建流程、脚本和定时任务等管理功能。后端是 Spring Boot 3.2.5 多模块 Maven 项目，REST API 与静态前端资源集中在 `module-web`；前端使用 Vue 3、Vue Router、Element Plus 和 Axios。现有持久化方式以 JSON 文件为主，业务数据保存在 `data/` 目录的不同子目录中。

本变更面向自托管管理后台场景，目标是在不引入数据库、不改变现有部署模型的前提下，为管理页面和管理 API 增加单管理员登录保护，并在首次打开时引导用户完成管理员初始化。

## Goals / Non-Goals

**Goals:**

- 为管理后台增加登录保护，未登录用户不能访问受保护的 `/api/**` 管理接口。
- 首次打开时自动识别系统未初始化状态，并在统一认证页面引导创建管理员账号。
- 管理员信息沿用 JSON 文件持久化，密码只保存带 salt 的 PBKDF2 哈希。
- 使用服务端 Session 与浏览器会话级 Cookie 维护登录状态。
- 前端提供统一 `/auth` 页面，根据后端状态切换初始化表单和登录表单。
- 初始化成功后不自动登录，要求用户回到登录表单重新输入账号密码。
- 后台 header 展示当前管理员，并提供退出登录入口。

**Non-Goals:**

- 不支持多管理员账号、角色权限、账号禁用、密码找回或密码修改。
- 不引入 Spring Security、JWT、数据库或外部身份提供商。
- 不提供“记住我”或跨浏览器持久登录。
- 不改变订阅、Mihomo、Pipeline、脚本和定时任务等现有业务能力本身。
- 不自动重置损坏或遗失的管理员文件，避免形成绕过认证的隐式恢复路径。

## Decisions

### D1：认证入口使用统一 `/auth` 页面

- **选择**：前端新增统一 `/auth` 页面，启动或路由切换时请求认证状态；无管理员时显示初始化表单，有管理员但未登录时显示登录表单。
- **理由**：入口统一、用户路径短，避免独立 `/setup` 与 `/login` 带来的页面分叉，同时仍能通过文案清楚表达“首次使用，需要创建管理员”。
- **已考虑 alternative**：独立初始化页边界更清晰，但路由和流程更多；后台内初始化弹窗能复用布局，但未初始化时展示后台外壳会弱化安全边界。

### D2：登录态使用服务端 Session + 浏览器会话 Cookie

- **选择**：后端在 HTTP Session 中保存认证标记和用户名，浏览器通过会话级 Cookie 自动携带会话。
- **理由**：符合自托管后台使用场景，前端无需保存 token，关闭浏览器后会话自然失效。
- **已考虑 alternative**：JWT / Bearer Token 更适合开放 API，但要处理 token 存储、过期和刷新；固定密钥方案实现简单但安全边界弱。

### D3：MVP 仅支持一个管理员账号

- **选择**：系统只允许存在一个管理员账号，管理员数据保存为单文件 `data/admin/admin.json`。
- **理由**：当前项目更偏个人/自托管管理后台，单账号模型可降低 UI、接口和数据模型复杂度。
- **已考虑 alternative**：多管理员账号具备未来扩展能力，但会引入账号管理、禁用、审计和权限边界等额外范围；预留多用户结构会增加当前实现复杂度。

### D4：管理员信息沿用 JSON 文件持久化

- **选择**：新增管理员仓库读写 `data/admin/admin.json`，与现有业务数据的 JSON 文件仓库风格保持一致。
- **理由**：不改变部署和备份模型，用户已有的 `data` 卷即可覆盖管理员信息。
- **已考虑 alternative**：H2/SQLite 等嵌入式数据库更规范，但对当前单账号能力过重；环境变量配置不符合“首次打开引导初始化”的体验。

### D5：密码使用 PBKDF2 哈希保存，规则仅限制最小长度

- **选择**：密码至少 8 位；后端使用 JDK 自带 PBKDF2（如 `PBKDF2WithHmacSHA256`）生成带随机 salt 的哈希，保存算法、salt、hash 和迭代次数等验证参数。
- **理由**：避免明文存储和额外依赖，同时保持首次初始化门槛较低。
- **已考虑 alternative**：复杂度规则能提高弱密码门槛，但对个人部署可能增加阻力；只做非空校验过弱。

### D6：认证拦截使用 Spring MVC `HandlerInterceptor`

- **选择**：在 `module-web` 中新增 `AuthInterceptor`，拦截 `/api/**`，放行 `/api/auth/**`，要求其他管理 API 具备已认证 Session。
- **理由**：项目当前没有 Spring Security；拦截器足以覆盖单管理员 Session 门禁，依赖少、行为直观。
- **已考虑 alternative**：Spring Security 更完整，但默认行为和配置复杂度对当前 MVP 偏重。

### D7：初始化成功后不自动登录

- **选择**：`POST /api/auth/setup` 保存管理员后不写入认证 Session，前端提示初始化成功并切换到登录模式。
- **理由**：让初始化和登录成为两个明确动作，降低误以为“创建即登录”的安全歧义。
- **已考虑 alternative**：自动登录体验更顺滑，但安全语义不如重新登录明确；成功页再点击进入会拉长流程。

## Risks / Trade-offs

[Risk] 自定义认证缺少 Spring Security 的完整防护能力 → Mitigation: 限定范围为单管理员自托管后台；明确拦截所有 `/api/**` 管理接口；密码使用 PBKDF2；后续如需要多用户或更复杂策略再评估引入 Spring Security。

[Risk] JSON 管理员文件损坏会导致无法登录 → Mitigation: 后端返回明确错误，不把损坏文件当作“未初始化”，避免攻击者通过破坏文件触发重新初始化；恢复依赖管理员从数据卷备份或手动维护文件。

[Risk] 未初始化状态下的受保护 API 语义容易混淆 → Mitigation: `/api/auth/status` 是唯一用于判断初始化状态的公开接口；其他管理 API 保持需要认证，不允许未初始化绕过。

[Risk] 前端路由守卫和 Axios 401 拦截可能产生跳转循环 → Mitigation: `/auth` 路由不再触发进入后台的强制跳转；认证接口自身的 401 只展示表单错误，不由全局拦截器二次跳转。

[Trade-off] 只支持一个管理员降低了多人协作能力 → 接受理由：MVP 聚焦个人/自托管后台，避免引入账号管理和权限模型。

[Trade-off] 浏览器会话级 Cookie 关闭浏览器后失效 → 接受理由：符合用户选择的偏安全会话策略，不提供“记住我”。

## Migration Plan

1. 新增后端认证模型、JSON 仓库、密码哈希工具、服务、控制器和拦截器。
2. 新增前端认证 API、认证状态管理、`/auth` 页面、路由守卫、Axios 401 处理和后台退出入口。
3. 补充后端测试，覆盖初始化、重复初始化、短密码、登录成功/失败、未登录拦截、登录后访问和登出失效。
4. 运行 Maven 测试与前端构建验证。
5. 部署后首次访问会出现初始化表单；已有部署没有 `data/admin/admin.json` 时会进入首次初始化流程。

Rollback 策略：回滚代码后，`data/admin/admin.json` 可保留在数据目录中但旧版本不会读取；如需完全回到无认证状态，回滚应用版本即可。验收条件是未登录不能访问受保护 API，初始化与登录流程按设计完成，现有业务页面在登录后仍可正常使用。

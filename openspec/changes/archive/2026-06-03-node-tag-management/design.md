## Context

当前订阅详情页的"代理节点"Tab 通过前端硬编码的 `FLAG_REGION_MAP`（约30个 emoji 映射）对节点进行地区分组。大量节点因命名不含 emoji 或使用了未收录的 emoji 而被归入"其他"。系统需要一个可配置的标签管理功能，让用户自定义匹配规则对节点进行分类。

技术栈：后端 Java 21 + Maven，前端 Vue 3 + Element Plus + TypeScript，数据存储为 JSON 文件。

## Goals / Non-Goals

**Goals:**
- 提供全局节点标签管理（CRUD），标签包含名称、优先级、匹配规则
- 在订阅详情页用标签替代硬编码的 `FLAG_REGION_MAP` 进行节点分组
- 支持优先级排序，按优先级顺序匹配，第一个命中即停止
- 未命中任何标签的节点归入"其他"兜底

**Non-Goals:**
- 不改变 Pipeline 架构或 build 流程
- 不在后端做标签匹配（纯前端）
- 不为节点模型添加持久化标签字段
- 不做自动标签推断/机器学习分类

## Decisions

### D1：全局标签 vs 订阅级标签

- **选择**：全局标签，所有订阅共享同一套标签配置
- **理由**：大多数节点命名有通用规律（国家名、地区代码），跨订阅通用；全局管理更简单
- **已考虑 alternative**：订阅级标签——每个订阅源独立配置标签，灵活但管理成本高，大多数场景下不必要

### D2：匹配冲突处理

- **选择**：支持优先级字段（数字，越小越优先），按优先级顺序遍历，第一个命中即停止
- **理由**：用户可精确控制匹配顺序；"其他"作为兜底
- **已考虑 alternative**：多标签匹配（一个节点可属于多个标签）——增加了 UI 复杂度，当前场景只需单标签分组

### D3：匹配执行位置

- **选择**：纯前端匹配，后端仅提供标签 CRUD API
- **理由**：改动最小，不影响现有后端架构；标签数据量小，前端获取后在 `computed` 属性中实时匹配即可
- **已考虑 alternative**：后端匹配返回带标签的节点——需要改动 API 返回结构，影响面大

### D4：存储方案

- **选择**：JSON 文件存储（`data/node-tags/{id}.json`），与现有 Subscription、MihomoInstance 一致
- **理由**：保持架构一致性，无需引入数据库
- **已考虑 alternative**：单文件存储所有标签——简化但不利于并发操作

### D5：标签管理 UI 位置

- **选择**：独立路由页面（如 `/node-tags`），在侧边栏导航中添加入口
- **理由**：标签管理是独立功能模块，需要表格展示 + 增删改操作，放入独立页面更清晰
- **已考虑 alternative**：嵌入订阅详情页——空间不足，且标签是全局的不应绑定到某个订阅

## Risks / Trade-offs

- [Risk] 节点名不含任何可匹配关键词时无法自动归类 → Mitigation: 预置常见国家/地区标签作为开箱即用配置，用户可自行补充
- [Risk] 大量标签时前端匹配性能 → Mitigation: 标签数量通常在几十个级别，对 `computed` 属性无性能影响
- [Trade-off] 纯前端匹配意味着 Pipeline 阶段无法利用标签 → 接受：当前需求仅用于展示分组，Pipeline 有独立的 Processor 体系

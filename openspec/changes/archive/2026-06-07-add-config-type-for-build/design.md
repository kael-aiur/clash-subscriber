## Context

### 背景
当前构建流程（BuildPipeline）只支持订阅源模式，需要选择主订阅和额外订阅。用户希望支持直接选择配置管理对象（ConfigProfile），简化配置流程，并确保每次构建都使用最新的配置。

### 现状
- **BuildPipeline 模型**：包含 primarySubscriptionId 和 additionalSubscriptionIds 字段
- **执行流程**：拉取主订阅配置 → 合并额外订阅节点 → 脚本处理 → 推送到 Mihomo
- **ConfigProfile 模型**：包含订阅源列表、代理组配置、规则组等，可通过 ConfigGeneratorService.generate() 生成完整配置

### 约束
- 保持向后兼容性，现有 BuildPipeline 自动迁移为订阅源模式
- 每次构建都重新生成配置，不使用缓存
- 配置组合模式下仍然支持脚本处理

### 利益相关者
- 用户：需要简化配置流程，直接选择配置管理对象
- 开发团队：需要最小改动，保持代码可维护性

## Goals / Non-Goals

**Goals:**
1. 为构建流程增加配置类型选择（订阅源模式/配置组合模式）
2. 配置组合模式下，直接选择 ConfigProfile 对象
3. 每次构建都重新生成配置，不使用缓存
4. 保持向后兼容性，现有构建流程自动迁移为订阅源模式
5. 配置组合模式下仍然支持脚本处理

**Non-Goals:**
1. 不重构为策略模式或组合模式（未来需要时再考虑）
2. 不修改 ConfigGeneratorService 的缓存策略
3. 不支持配置组合模式下的额外订阅合并

## Decisions

### D1：扩展 BuildPipeline 模型
- **选择**：在 BuildPipeline 模型中增加 configType 和 configProfileId 字段
- **理由**：
  - 改动最小，保持现有架构
  - 向后兼容性好，现有数据自动迁移
  - 实现简单，风险低
- **已考虑 alternative**：
  - 策略模式：代码结构清晰，但改动较大，需要重构
  - 组合模式：灵活性最高，但改动最大，实现复杂

### D2：配置组合模式直接生成完整配置
- **选择**：调用 ConfigGeneratorService.generate(profile) 直接生成完整的 Clash 配置
- **理由**：
  - 配置组合已经包含完整的配置信息（订阅源、代理组、规则组）
  - 避免重复处理，提高效率
  - 保持配置组合的完整性
- **已考虑 alternative**：
  - 提取订阅源后按现有流程处理：会丢失配置组合中的代理组和规则组配置

### D3：每次构建重新生成配置
- **选择**：每次构建都调用 ConfigGeneratorService.generate() 生成配置，不使用缓存
- **理由**：
  - 确保每次构建都使用最新的配置
  - 避免缓存导致的配置不一致问题
  - 满足用户需求
- **已考虑 alternative**：
  - 使用缓存：可能返回过期配置，不满足需求

### D4：向后兼容性自动迁移
- **选择**：现有 BuildPipeline 的 configType 字段为 null 时，自动迁移为 "subscription"
- **理由**：
  - 保持向后兼容性，无需手动修改现有数据
  - 自动迁移逻辑简单，风险低
  - 用户无感知，体验好
- **已考虑 alternative**：
  - 不迁移：需要用户手动修改，体验差

### D5：配置组合模式支持脚本处理
- **选择**：配置组合模式下仍然支持脚本处理
- **理由**：
  - 提供灵活性，用户可以在配置组合生成后进一步修改配置
  - 保持两种模式的一致性
  - 脚本处理是可选功能，不影响核心流程
- **已考虑 alternative**：
  - 跳过脚本处理：限制了用户的灵活性

## Risks / Trade-offs

### 风险
1. **数据库迁移失败** → Mitigation: 准备回滚脚本，备份数据库
2. **向后兼容性问题** → Mitigation: 自动迁移逻辑，充分测试
3. **配置组合模式执行失败** → Mitigation: 详细日志记录，快速回滚
4. **定时任务异常** → Mitigation: 监控告警，手动触发验证

### 取舍
1. **模型复杂度 vs 功能需求** → 接受理由：增加 configType 和 configProfileId 字段是必要的，虽然增加了模型复杂度，但满足了功能需求
2. **条件分支 vs 代码结构** → 接受理由：执行逻辑中的条件分支是不可避免的，但通过清晰的方法分离可以保持代码可读性

## Migration Plan

### 部署步骤
1. **数据库迁移**
   - 执行 SQL 迁移脚本，新增 config_type 和 config_profile_id 字段
   - 创建索引
   - 更新现有数据，设置 config_type 为 'subscription'

2. **代码部署**
   - 部署新版本代码
   - 验证服务启动正常
   - 验证 API 接口正常

3. **数据验证**
   - 检查现有 BuildPipeline 数据
   - 验证 config_type 字段已正确设置
   - 验证向后兼容性逻辑正常工作

4. **功能验证**
   - 测试订阅源模式构建流程
   - 测试配置组合模式构建流程
   - 验证定时任务正常执行

### 回滚方案
1. 删除索引
2. 删除新增字段
3. 验证回滚结果

### 验收条件
1. 数据库迁移脚本执行成功
2. 现有数据已迁移（config_type 不为 null）
3. 订阅源模式构建流程测试通过
4. 配置组合模式构建流程测试通过
5. 定时任务正常执行
